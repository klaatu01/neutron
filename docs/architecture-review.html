Architecture review

Rewiring Neutron

Every message in the client — from every producer, to every consumer, across every broker — passes through one task. That single decision sets the throughput ceiling, the latency floor, the failure domain, and the reason reconnection was never written. Here is the shape high-throughput clients take instead.

Current shape

One task in the middle of everything

The architecture is a central dispatcher: a single tokio::select! loop in Pulsar::start_pulsar that relays between every client and every broker connection. It is a genuinely attractive pattern, and it is worth being precise about why before replacing it.

A hub gives you one place where ordering is defined, and it makes shared state safe for free — client → broker mappings can be plain fields because exactly one task ever touches them. For a first working client that is the right call. You got a correct protocol implementation out of it, which is the hard part.

What it costs is everything that scales. The hub is a serialization point, so throughput is capped at one core no matter how many runtime threads you give it. It is a single failure domain, so one Err from one client ends the loop and every producer and consumer in the process with it. And it adds a hop that buys nothing: by the time a producer's payload reaches the hub, the destination connection was already known at the source.

Patterns

Five moves that carry the throughput

These are the load-bearing patterns in high-throughput async Rust services. None are exotic; all of them are things the current design either inverts or skips.

Actor per resource, split by direction

one task for the system → two tasks per connection

The unit of concurrency should be the thing that can independently block — a socket — not the system as a whole. Split each Framed into its SplitSink and SplitStream and run a reader task and a writer task over the halves.

Two tasks rather than one select! is the part people skip, and it matters for throughput: a slow flush can no longer delay decoding, neither direction can starve the other on readiness, and you drop the whole class of cancellation-safety hazards that come from awaiting composite futures in a loop. N connections then genuinely use N cores, because nothing they share is on the hot path.

Coalesce at the syscall boundary

one flush per message → one flush per batch

This is usually the single largest throughput win available in a protocol client, and it is invisible in the type system. A writer task that owns the sink should drain its queue with recv_many(), feed() every frame into the encoder, and flush() exactly once for the batch.

Under load the batch size grows on its own — that is the point. Cost per message falls as offered load rises, which is precisely the curve you want and the opposite of what a per-message send().await gives you. Note this is a different mechanism from protocol-level producer batching, which the codebase already has; you want both, and they compose.

Route by lookup, not by traversal

poll N receivers → index one map

select_all over a Vec of receivers is O(N) allocation and O(N) polling per message, and it polls in index order, so early clients starve later ones under sustained load. It is the wrong shape twice over.

Both directions have a cheaper form. Outbound, let the senders converge: that is what a multi-producer channel is for — N senders, one bounded queue, one receiver. Inbound, don't converge at all: the frame already carries its consumer_id or producer_id, so the reader task can index a concurrent map and hand the message straight to that client's inbox. O(1), no intermediary, no shared cursor.

One buffer, many owners

Vec<u8> cloned per hop → Bytes refcounted

Payloads are Vec<u8> and get cloned at every relay — three full copies inbound and three outbound. At 1 MB messages that is 6 MB of memcpy per message round trip, all of it pure overhead.

bytes is already a dependency. Decode with BytesMut::split_to(n).freeze() so the payload is never copied out of the read buffer, and make Bytes the payload currency through every layer. Every subsequent hop becomes an atomic increment. In a broker client this is not an optimization, it is the baseline the rest of the design assumes.

Bounded queues are the flow control

async_channel::unbounded → bounded, with a stated policy

Every channel in the system is unbounded (engine.rs:28-29). An unbounded queue does not remove backpressure; it relocates it to the allocator, where it surfaces as an OOM instead of a slowdown. It also destroys tail latency, because queue depth — and therefore time-in-queue — has no limit.

Bound every queue and state its policy per direction. Outbound, a bounded send().await propagates pressure to the application, which is exactly what you want. Inbound, the capacity must be the same number as the flow-control credit you grant the broker — the most commonly missed coupling in message-client design. If credit exceeds capacity the queue overflows; if capacity exceeds credit you stall below your configured rate. Tie them together and issue new credit as the application drains.

Multiplexing

The in-flight table

Any client that multiplexes many logical streams over one socket needs the same structure: a table of requests awaiting a response. HTTP/2 keys it on stream id, AMQP on channel, JDBC on statement handle. It is worth getting the shape exactly right, because everything about reliability under load flows through it.

Neutron's CommandResolver keys this table on a string derived from the command type — "ACK", "SUBSCRIBE", format!("SEND:{}", sequence_id) — in one map shared by every client in the process. That has a throughput cost (an allocation and a string hash on every publish, on the hot path) and a correctness cost that matters more: type names are not unique per request, so concurrent requests of the same kind collide in the map.

The pattern has three properties, and each one is doing real work:

  1. Key on an identifier the protocol echoes back. The wire format already carries request_id for exactly this purpose. A u64 key costs no allocation and no formatting, and it is unique per request by construction rather than by convention.
  2. Scope the table to the connection. Request ids are only unique within a connection, and a shared process-wide table makes every client contend on one lock for a structure that has no reason to be shared.
  3. Give every entry an owner that must complete it. An entry leaves the table on response, on deadline, or on connection teardown — never any other way. Miss the second and a lost response hangs a caller forever; miss the third and it hangs them until process exit. Neutron defines OperationTimeout in its error enum and never constructs it, and nothing sweeps the map, so entries only ever leave on a successful match.

Concretely: HashMap<u64, Pending> behind a short-lived lock, where Pending holds the oneshot::Sender, a deadline, and enough context to write a useful error. One tokio::time::interval per connection sweeps expiries. On teardown the supervisor drains the whole table and completes every waiter with a disconnect error. No hangs, no leak, no shared lock.

Reliability

Reconnection is a topology property

Automatic reconnection is the one unchecked box in the README. It is worth saying plainly: it isn't missing because nobody wrote it. The current topology excludes it.

EngineConnection::pair() bonds a client to a connection by handing each side two channel endpoints. That is a point-to-point binding — the client's only route to the broker is that pair of channels. When the connection task exits the endpoints close, and there is nowhere to put a replacement, because the client holds a wire rather than an address.

The pattern that fixes it is indirection: a client should hold a name, not a wire. Give it a key into a registry, or an ArcSwap<ConnectionHandle>, and a supervisor can swap a fresh connection in behind that name while the client is mid-flight. This generalizes past this codebase — anything you want to be able to restart at runtime has to be addressed indirectly.

Supervision, not spawn and hope

Long-lived tasks here are spawned detached, so when one exits nobody observes it. Give every long-lived task a parent that holds its JoinHandle, classifies the exit, applies jittered exponential backoff, and restarts it. Pair that with a CancellationToken so shutdown propagates, and a TaskTracker or JoinSet so shutdown can be awaited rather than assumed.

The retry decision belongs in the error type, not in each call site. A fn retryability(&self) -> Retryability returning transient, permanent, or fatal lets one backoff loop serve every path, and it stops the current situation where ChannelTerminated means both "the broker went away" and "your waiter was evicted" — two conditions with opposite correct responses.

Proposed

The target shape

Put the five patterns together and the hub disappears. What replaces it is not another task — it is a shared table that clients and readers index directly. Nothing sits between a producer and its socket.

Reference

Choosing the primitive

Most of the design pressure in a service like this resolves into picking the right channel and the right sharing strategy. The codebase currently uses one primitive — an unbounded MPMC channel — for jobs that want five different ones.

When you needReach forNot
Many senders, one owner of a resource bounded tokio::sync::mpsc anything unbounded
One request, one reply oneshot + table keyed on the protocol's id a shared map keyed on command type
N workers competing for the same jobs async_channel (true MPMC) mpsc plus manual sharding
Same value to every subscriber broadcast cloning into N mpsc senders
Latest-value state (current broker, config) watch or ArcSwap Mutex<T> read on the hot path
Read-mostly map on the hot path sharded RwLock<HashMap> or DashMap one process-wide Mutex
State exactly one task touches plain ownership, no lock at all Mutex for reassurance

That last row is worth dwelling on. Pulsar wraps its two managers in futures::lock::Mutex even though a single task owns them, and then holds both guards across a select!. The locks buy nothing and cost a guard held across every await in the loop. The idiomatic rule in async Rust is ownership over locking: give state exactly one owner, use a lock only for genuinely shared read-mostly data, and never hold a guard across I/O.

Counterpoint

When a central dispatcher is the right answer

It would be dishonest to present the hub as simply wrong. It is the correct pattern when you need global ordering across clients — a total order that no per-connection design can give you. It is correct when the number of participants is small and fixed, where O(N) traversal is a handful of pointer derefs. And it is correct when the shared-state mutation rate is high relative to the message rate, because then the serialization you are paying for is doing real work.

A messaging client is none of those. Ordering guarantees are per topic and per producer, and they are enforced by sequence ids on the wire rather than by client-side scheduling. The participant count is unbounded and user-controlled. And the shared state — which broker owns which topic — changes on lookups and reconnects, which are rare relative to messages. The traffic is almost pure message passing over almost static routing state, which is the exact profile that wants a shared table and no hub.

Measured

Benchmarked against the C++ client

Claims about throughput patterns deserve numbers. Both clients were run against the same lightweight protocol server — the crate's fake broker, serving the wire protocol over real TCP through the production codec in a separate process — so the broker cancels out and the difference is client overhead, which is what this document is about.

Matched harnesses: producers publish with a 1,000-message in-flight cap and await every receipt; consumers measure delivery throughput with flow control live (neutron grants 500 credits, re-granted past the halfway mark; the C++ client was configured to the same 500-slot receiver queue) and the clock starting at the first message. Four runs per configuration against a fresh broker each; the first is warmup, the number reported is the median of the remaining three.

What the numbers say — and what they don't

The unbatched-producer column is the coalesced flush doing exactly what Fig 3 promised: neutron's writer drains its queue and flushes once per batch even for individually-published messages, while the C++ client writes each unbatched message separately — which is precisely why its defaults turn protocol batching on. With both sides batching, the gap narrows to the per-message bookkeeping and copies, and neutron still clears 1.6M receipts per second. The consumer matchups tighten as payloads grow — at 4 KB the work is dominated by moving bytes, which both clients ultimately delegate to the kernel.

Honest caveats: this is a client-overhead microbenchmark, not an end-to-end broker benchmark — the server is featherweight and co-located, so absolute numbers will not survive contact with a real cluster, though the client-side ratios should. The C++ client ran its shipped defaults (one IO thread per connection, which is its architecture, not a misconfiguration). And both harnesses live in the repo (bench/run.sh), so the numbers are reproducible rather than anecdotal.

Sequencing

An order that ships

Each stage stands alone, keeps the public API, and is worth landing on its own. Nothing here requires a rewrite, which matters — the protocol layer is the part that took the work, and none of it needs to change.

Stage 1

Move correlation onto request_id

HashMap<u64, Pending> scoped per connection, with a deadline on every entry and an interval that sweeps expiries. Drop the string keys. Removes an allocation and a hash from every publish, and makes concurrent same-kind requests well-defined.

Stage 2

Bound the channels, make payloads Bytes

Capacities become a config surface. Decode with split_to().freeze() and delete the relay clones. Purely mechanical, no topology change, and the memcpy disappears.

Stage 3

Split reader and writer, add the coalescing flush

Two tasks per connection over a split Framed. recv_many + feed + one flush. This is where the throughput curve changes shape.

Stage 4

Introduce the registry, retire the hub

Readers route by id straight to client inboxes; clients hold handles and publish straight to writer queues. Pulsar::start_pulsar, ClientManager and ConnectionManager all go away. Dispatch now scales with cores.

Stage 5

Supervise, reconnect, replay

Per-broker supervisor with jittered backoff and session replay, retryability on the error type, and consumer credit tied to inbox capacity. Ticks the last two boxes on the README.

The one-sentence version

Stop moving messages through a task and start moving them through a table: give every socket its own reader and writer, let senders converge into bounded queues instead of making a receiver poll them, key in-flight requests on the id the protocol already gives you, pass payloads by refcount, and put a supervisor over anything that can die.

Everything above is a change to how the pieces are wired. The protobuf layer, the codec, the builders and the public API survive it — which is the argument for doing it now, while the surface is still small.
